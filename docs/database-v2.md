# Recruiting database v2

The new tables coexist with the current application tables:

| Table | Purpose | Sample rows |
| --- | --- | --- |
| `public.recruits_v2` | Player profiles, academics, basketball, contacts, and health information | 50 |
| `public.staff_members_v2` | Approved staff profiles and optional login-account links | 3 |
| `public.recruit_notes_v2` | Evaluations, interactions, general notes, and medical notes | 150 |
| `public.recruit_other_offers_v2` | Other schools' offers, date learned, and source | 75 |
| `public.recruit_visits_v2` | Visit type, date, Planned/Completed status, and details | 60 |
| `public.recruit_pipeline_history_v2` | Automatic attributed history of pipeline, offer, and visit changes | Generated by triggers |

The migration only creates new objects. It does not alter or delete the original tables, migrate their records, or change their permissions. The existing website continues using its current tables until its queries and forms are switched over in a separate change.

## Files and application

- Schema: [`20261103120000_recruit_schema_v2.sql`](../my-app/supabase/migrations/20261103120000_recruit_schema_v2.sql)
- Fictional data: [`seed-v2.sql`](../my-app/supabase/seed-v2.sql)
- Database tests: [`tests/schema-v2.sql`](../my-app/supabase/tests/schema-v2.sql)

With Docker and local Supabase running, apply pending migrations from `my-app/` with `npx supabase migration up --local`. Applying the migration creates the tables; inserting the sample records is a separate step. The local seed configuration includes both seed files for newly initialized databases. Do not reset an existing database to load these samples: a reset discards its data.

For an existing hosted database, first confirm it has the earlier migrations recorded before using `supabase db push`. Earlier migration files include changes to the original tables, so do not blindly apply the full migration history to a database with unknown migration status.

To apply only the new schema and sample data through a direct administrator connection, set `HOOP_V2_DATABASE_URL` privately in your shell, then run these commands from `my-app/`:

```bash
psql "$HOOP_V2_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/migrations/20261103120000_recruit_schema_v2.sql
psql "$HOOP_V2_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed-v2.sql
```

Alternatively, execute the contents of those two files, in that order, in the intended project's Supabase SQL Editor. Run the schema file once. The seed file can be rerun: fixed IDs and `ON CONFLICT DO NOTHING` avoid duplicates and preserve edits to existing sample rows. The fake dataset is for development/test databases.

If applying the schema manually, record migration `20261103120000` as applied using the CLI's migration repair command for that same project before subsequently using migration-based deployment. Do this only after confirming the schema transaction succeeded. This avoids trying to create the same tables twice.

The repository's public publishable/anon key cannot create tables. Applying this SQL requires a database administrator connection or authenticated Supabase management access.

## Data and relationships

`recruits_v2` stores names, birthday, height in inches, weight in pounds, positions, jersey number, school, graduation year, GPA and GPA scale, academic information, location, club team, circuit, age group, player contact information, guardian contacts, media links, medical notes, recruiting status, and timestamps. Age is calculated from birthday rather than stored. Unknown values can remain NULL. GPA must be within its specified scale.

`recruit_notes_v2.recruit_id` references `recruits_v2.id`; `author_id` references `staff_members_v2.id`. Notes have a category, optional title, required body, observation date, and creation/edit timestamps. Editing a note cannot reassign its author or recruit. An index supports retrieving notes for a recruit in date order:

```sql
SELECT n.*, s.display_name AS author_name
FROM public.recruit_notes_v2 AS n
JOIN public.staff_members_v2 AS s ON s.id = n.author_id
WHERE n.recruit_id = 'a2000000-0000-4000-8000-000000000001'
ORDER BY n.occurred_at DESC, n.created_at DESC;
```

All sample people, schools, clubs, observations, and health details are fictional. Emails and media links use `example.com`, and phones use the reserved fictional 202-555-01xx range. Profiles vary across positions, graduation years 2027–2030, height, GPA, and recruiting status. Every player has three notes attributed to the sample staff.

## Staff accounts and permissions

Sample profiles are Dana Mercer (admin), Robin Ellis (staff), and Casey Rowan (staff). They have no login accounts or passwords. `staff_members_v2.id` identifies the profile; nullable, unique `user_id` links it to a real Supabase Auth account. A profile with no account cannot authenticate or grant access.

After creating your real account through the app, a trusted database administrator can grant v2 access without changing the original staff table:

```sql
INSERT INTO public.staff_members_v2 (user_id, display_name, role)
SELECT id, 'Your name', 'admin'
FROM auth.users
WHERE email = 'your-account@example.com';
```

- Active staff can read all v2 profiles and notes, including medical information, and create/edit recruits.
- Notes must be attributed to the currently authenticated staff member. Staff can edit/delete their own notes; admins can edit/delete all notes.
- Only admins can delete recruits, because that deletion also removes the recruit's notes.
- Staff membership is managed through trusted administrative operations, not client writes.
- Setting `is_active = false` removes access while retaining note authorship. Deleting an Auth account clears its profile's `user_id`; deleting a staff profile with notes is blocked.

## Verification

Run the database tests after applying the migration and seed, as the database owner:

```bash
psql "$HOOP_V2_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/schema-v2.sql
```

The tests create temporary test account rows inside a transaction and roll everything back. They verify sample counts, note relationships, validation, anonymous/nonstaff/inactive access denial, staff access, authorship, privilege escalation prevention, administrator edits, and cascading deletion. Use a development/test database for verification.

## Pipeline, offers, and visits

The follow-up migration [`20261103140000_recruit_pipeline_v2.sql`](../my-app/supabase/migrations/20261103140000_recruit_pipeline_v2.sql) adds:

| Display label | `recruits_v2.pipeline_stage` value |
| --- | --- |
| Identified | `identified` |
| Evaluating | `evaluating` |
| Priority | `priority` |
| Offered | `offered` |
| Committed to USNA | `committed_to_usna` |
| Committed Elsewhere | `committed_elsewhere` |
| Not Pursuing | `not_pursuing` |
| To be confirmed | `to_be_confirmed` |

`pipeline_stage` is the new pipeline source of truth. The older `recruiting_status` column is retained for compatibility and is not synchronized; new application features should use `pipeline_stage`.

A USNA offer is stored as `usna_offer_date` and `usna_offered_by_staff_id`. Both must be filled or both empty. Each other-school offer has its own row with `school`, `date_learned`, and `source`. Each visit has `visit_type` (`official`, `unofficial`, `campus_tour`, `home`, `school`, or `other`), `visit_date`, and `status` (`planned` or `completed`).

Until F12, the application must provide an active staff-name selection on every save. Use `pipeline_changed_by_staff_id` for a recruit's pipeline/USNA offer and `changed_by_staff_id` for other offers and visits. Populate that selection with:

```sql
SELECT id, display_name FROM public.staff_members_v2
WHERE is_active ORDER BY display_name;
```

Supply the selected staff ID together with the changed fields in the same INSERT/UPDATE. This is staff-selected attribution, not proof that the selected person logged in. Existing RLS still requires an approved, active account for application access. History also records the actual authenticated account when available, so F12 can later enforce account-based attribution.

For example, to change a recruit's stage:

```sql
UPDATE public.recruits_v2
SET pipeline_stage = 'priority',
    pipeline_changed_by_staff_id = 'b2000000-0000-4000-8000-000000000002'
WHERE id = 'a2000000-0000-4000-8000-000000000001';
```

Database triggers record changes in `recruit_pipeline_history_v2`, including the selected staff ID, name at the time, server timestamp, and before/after values. Business dates such as visit date and date learned are separate from the timestamp when a change is saved. Existing/unassigned profiles default to `to_be_confirmed` without inventing a past author or change event. Unrelated profile fields and free-text notes use their existing tracking behavior; this history covers the new pipeline/offer/visit features.

Clients can read history but cannot insert, edit, or delete it directly. Offers and visits are archived with `archived_at = now()` and the selected staff ID; normal lists should filter `archived_at IS NULL`. Archiving is recorded as an update. Recruits with recorded pipeline activity cannot be hard-deleted because their history must remain available. Their stage can be changed to `not_pursuing`.

```sql
SELECT entity_type, action, changed_at, staff_name_at_change, before_values, after_values
FROM public.recruit_pipeline_history_v2
WHERE recruit_id = 'a2000000-0000-4000-8000-000000000001'
ORDER BY changed_at DESC, id;
```

[`seed-pipeline-v2.sql`](../my-app/supabase/seed-pipeline-v2.sql) assigns all 50 sample recruits to stages and inserts 75 fictional other-school offers and 60 fictional visits. Sample USNA offers appear on Offered/Committed to USNA profiles. School names may be real institutions, but all offer and visit claims are fictional. History timestamps reflect when the sample script runs, not a claimed historical edit date. Rerunning the seed preserves existing edits and does not duplicate history.

Apply the follow-up migration before running that seed file. The local seed configuration runs it after `seed-v2.sql`. Run [`tests/pipeline-v2.sql`](../my-app/supabase/tests/pipeline-v2.sql) to verify stage constraints, attributed changes, history protection, staff-only access, and archiving; the test rolls back its temporary changes. The frontend still needs forms and staff selectors wired to these new fields and tables.
